# Connected Map redesign

## Scope and constraints

Prompt 1 builds on the existing Prompt 0 tokens, GlassBar, category identity, AvatarStack, Card, ProgressBar, Skeleton, EmptyState, Toast, motion preferences and tab geometry. Preserve every pre-existing uncommitted change and keep `docs/UI_REDESIGN_PLAN.md` unchanged. This is a presentation and interaction change: preserve production models, queries, permission checks, recipient APIs, RSVP capacity rules, route names and other consumers of the existing detail panel. No RLS, RPC or access-model changes.

Native is the primary implementation: Apple Maps on iOS with muted standard appearance and active light/dark mode; Google Maps on Android with palette-aware light/dark JSON styling. Remove the brown overlay. Web receives matching light/dark CARTO tiles and proper OpenStreetMap/CARTO attribution, but browser checks do not establish native acceptance. Expo SDK 57 documentation and installed react-native-maps 1.27.2 APIs govern implementation. Use FlashList 2.0.2 and Supercluster.

## Screen behavior

- Full-bleed map under a translucent status bar. A 48-point, radius-24 GlassBar search pill includes a 44-point compass button. Inline search groups readable Beacons, People and Places and includes actual saved places and session query history. Do not invent saved data or history records.
- Scrollable All / Friends / Squads / Public / Now rail with animated selection, pinned Filters action and advanced-filter count. Removable chips represent all active advanced filters. Remove the former header stats, List button, cramped dropdown and Nearby sheet.
- Vertically centered 44-point Layers / Locate / Fit results controls, 12-point gaps. Layers changes supported map appearances. Locate opens Compass; only its Use my location action requests foreground location. Compass also offers overview, everywhere and inline other-place search with saved places/recents. Explain centering versus sharing; denial gets inline copy and Settings action.
- Search this area appears after camera displacement or scale change of approximately 25% of the viewport, with loading and brief result-count feedback. Keep stable queried exploration area separate from the immediately visible camera bounds: panning updates the visible list without implicitly changing the query area or access rights.
- Persistent nonmodal Gorhom results sheet has 96-point / 50% / full snaps. Peek shows actual Beacon/Plan counts and a List toggle. Half/full show FlashList rows with category, title, host, actual time/countdown, available distance, going avatars, actual remaining capacity and inline RSVP. Loading uses skeletons and chip shimmer; empty shows Nothing here yet with Clear filters/Search wider; offline and location denial use slim inline feedback.
- Filter sheet has When (Any/Today/Tonight/Tomorrow/Weekend), multi-select categories, Join (Any/Open/Needs People/I'm In), and a More accordion exposing existing people/community/audience/place/plan filters. Keep selections during the session, reuse existing filter semantics, and provide sticky Reset/Show N Beacons actions with live counts.
- Selection connects markers, list and preview. Row selection animates the camera and selects a pin; pin selection scrolls its row into view. A horizontal snapped preview carousel moves selection/camera between nearby visible Beacons. The floating radius-24 glass card uses 16-point gutters above the tabs and shows category, host, title, live time, location, available distance, avatars and capacity progress. Card tap/swipe up opens existing Beacon detail with a reduced-motion-safe scale/fade; swipe down or map tap dismisses. Physical destinations retain the existing destination-only directions link.
- RSVP uses existing going/interested/withdraw/request actions. Primary reads Request to join when approval is required; full capacity does not offer a nonexistent waitlist. Successful actions receive supported haptic/check feedback and show actual updated state. Respect activity and meeting-detail read permissions everywhere, including search, rows, markers, previews and detail.
- Split the old ambiguous Sharing/My Beacon presentation. Show a Sonar pill only for an active actual session, with real recipient count and remaining time, green pulse respecting reduced motion, and existing recipient/Extend/Stop controls. A separate clearly named own-Beacon action may remain if needed. No location acquisition or sharing occurs on pan, locate-button opening or implicit screen load.
- Keep the Prompt 0 tabs and Squads badge; add a subtle Create pulse once per app session on the first launch presentation, disabled by reduced motion.

## Map rendering and data contracts

Replace teardrops with 40-point category-ring/icon badges and a downward notch. Now Beacons receive a two-second reduced-motion-aware halo; street-level zoom reveals compact time chips. For Android's bitmap-backed custom markers, use static memoized marker content and a lightweight Reanimated native map Circle overlay for the halo after confirming installed MapCircle support. A continuously animated marker child cannot remain live under tracksViewChanges=false. Selection scales to 1.25 with brief tracking during the spring or a supported projected overlay, gives a light supported haptic and dims other pins to 70%. Trigger bounded marker redraws on theme, selection and avatar-image changes, then stop tracking. Record animation limitations when the platform cannot reliably support the approach. Friend markers use 36-point avatars, actual availability rings and age labels only when explicitly shared, unexpired and updated within five minutes. Reuse Prompt 0 animated controls or a sliding indicator for chip-rail selection.

Supercluster consumes only readable and filtered Beacon points, produces count badges with category-mix segmented rings, fits expansion bounds on press, and requests a sheet containing the cluster members at maximum zoom. Bound rendered map features to approximately 150 using clustering; memoize markers and disable native tracksViewChanges after their initial render/update settles without freezing later real state updates.

No distance is inferred from an assumed user location. Show viewer distance only when a real explicit viewer location exists; otherwise omit it or clearly label distance from the exploration center. Accepted seat counts and capacity must match existing RSVP behavior, including host/approved-going semantics. Use actual available data for all counts, people, times and sharing labels.

## Three bounded implementation packets

1. **Screen composition and controls:** owns `MapScreen.tsx`, header/search/filter/Compass/sharing components and the small tab-pulse integration. Owns search/filter/camera-selection orchestration and permission checks. Supplies the filtered readable Beacon collection, visible collection, selected ID, camera region, viewer location when known, loading/offline state, RSVP callbacks and sharing facts to the other packets. Maintains existing semantic filters, adding only local category multi-select state if the old category model is single-valued. Owns the final integration edits to this screen.
2. **Map surface:** owns native/web `BeaconMap` implementations, clustering helpers and marker rendering. Preserves current camera methods (`animateToRegion`, `fitToCoordinates`) and viewport callbacks. Accepts the readable filtered collection and selected ID; emits Beacon selection, map dismissal, viewport changes and cluster-member requests. Adds optional callbacks/props without breaking existing consumers. Handles styles, feature bounds, native marker lifecycles, friend freshness and Supercluster bounds/maximum zoom behavior. Does not modify screen composition or list components.
3. **Results and preview:** owns new persistent results-sheet, row and preview-carousel components, adapting existing tooltip only if compatible with its consumers. Receives the visible Beacon collection, selected ID, existing permission-aware metadata and real action callbacks. Exposes imperative row scrolling and sheet snapping (including optional cluster member view); emits selection and detail/directions requests. Uses existing shared UI and FlashList. Does not modify `MapScreen.tsx`, map internals or the shared detail panel API.

Agree on exported prop/type additions before integration; helpers created for a packet stay in its owned area. The screen remains the selection source of truth so carousel, list and map cannot maintain competing selections. Cluster-member views clear when the query/filter/viewport changes. Review completed packets against these contracts and Prompt 1 before final validation.
